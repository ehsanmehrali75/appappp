# Shared manual ERP / SQL inventory contract

Version: `maarksho.erp.inventory.v1`. The existing manual ERP preview uses description, variant SKU, warehouse, size, color, price and stock; application products use `variants`, `sizes`, `stock_online`, `stock_total`, warehouse totals and `warehouse_details`. SQL input is adapted to that format by `ERPInventoryContract`.

A normalized SQL row is exported with the aliases the manual intake already consumes: `ProCode`/`sku`/`product_code`, `ProDes`/`name`, `AnbarCode`/`anbar_code`, `AnbarName`/`anbar_name`, `Color`/`color`, `size`/`sizes`, `StockTedad`/`stock_tedad`/`stock_online`/`stock_total`, and `NetItem`/`price` when price is actually supplied. `ModelCode`, `ColorCode`, source metadata and an explicit category path are retained. Exported prices are already converted to toman and are not converted again on reimport. Absent price stays absent. Missing size/color is not invented; Grade remains separate.

Rows carry `_erp_contract` so the manual parser preserves zero/decimal inventory instead of its legacy fallback, and the server dispatches these versioned rows through the same normalization/merge engine as SQL. Ordinary unversioned legacy imports keep their existing processing. All database access/role checks around those routes remain. Generated rows are not project backups and contain no account secrets.

Grouping uses stable ModelCode and ColorCode when supplied, with SKU-preserving per-size variants, aggregation across branches, naturally sorted sizes and the existing manual parent-SKU preference (size 3 for more than two variants, size 2 for two, otherwise the corresponding sorted variant). Matching includes existing variant SKUs; merging several legacy parent products is rejected for review. Changing a known SKU from an unknown size to a supplied real size supersedes its old placeholder variant, avoiding double stock. Conflicting model/color/size identities for one SKU are rejected.

Products expose both `warehouses` and persisted `warehouses_stock`, plus `warehouse_details` entries containing warehouse label/code, SKU, size, color and stock. Source metadata stays in the variants JSON and is restored on SQL-backed reload; explicit category paths also reconstruct `categories.gender/group/type`. Images and editorial text are preserved; new image-less products enter `pending` review with missing-media state. Missing-product zeroing remains the explicit per-project SQL option; the versioned path does not inherit unconditional legacy zeroing.

In Extraction Automation, configured SQL projects show the new connector under the existing Tiam tab. Settings still exposes it too. A valid preview offers **download JSON compatible with manual synchronization**. The export requires matching job ID, creator session, permissions, unexpired preview and unchanged configuration/product base; exporting performs no writes. Full normalized rows are kept privately and omitted from ordinary status responses. Export is invalid after application/cancellation/expiry or after a manual import changes the base.

The current FactInventory preset remains for the existing report. A separate complete-ERP preset maps the future Size, Color, ColorCode, ModelCode, AnbarCode/Name, NetItem and CategoryPath columns; use it only once the technical team supplies them. Its report name remains editable. See [the ready-to-send request](tiam-technical-request-fa.md).

Validation: pure PHP contract roundtrip tests, existing Tiam/FactInventory tests, and real local Chromium/HTTP/SQLite tests covering SQL preview export, identity/ownership guards, zero/decimal manual parsing, actual manual submit and persistence of variant/warehouse/category fields, plus rejection of stale exports. Test rows are synthetic; this does not establish that the live SQL report has acquired size/color/model columns.
