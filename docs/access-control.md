# نقش‌ها و دسترسی بخش‌ها

| نقش | محدوده | مجوز پایه |
| --- | --- | --- |
| `owner` | کل سامانه | مدیر کل بدون محدودیت؛ امکان تعمیر تمام تنظیمات دسترسی |
| `main_admin` / `superadmin` قدیمی | کل سامانه | مدیریت سراسری؛ وضعیت غیرفعال کامل را دور نمی‌زند؛ تنظیمات تعمیر همیشه باز است |
| `project_admin` | فقط پروژه‌های تأییدشدهٔ خودش | مدیریت بخش‌های فعال همان پروژه؛ بدون اختیار اعطای نقش سراسری |
| `manager` / `editor` | پروژه‌های تأییدشدهٔ خودش | ورود به مدیریت و کار با بخش‌های انتخاب‌شده؛ مدیریت اعضا فقط با مجوز کاربران و در حد اختیارات خودش |
| `viewer` | پروژه‌های تأییدشدهٔ خودش | مشاهدهٔ بخش‌های انتخاب‌شده؛ عملیات یک بخش فقط با اعطای صریح مجوز استفاده |

- `main_admin`: ادمین اصلی سامانه؛ `superadmin` قدیمی برای حفظ حساب‌های فعلی معادل آن است. نام کاربری `admin` به‌تنهایی هیچ امتیازی ایجاد نمی‌کند. نقش ادمین اصلی از فرم اعضای پروژه قابل تخصیص نیست.
- `project_admin`: مدیر همان پروژه؛ محدودیت‌های ادمین اصلی را دور نمی‌زند.
- `manager`: دسترسی به پنل مدیریت، فقط با مجوز بخش‌های انتخاب‌شده؛ اختیارات ادمین پروژه را ندارد.
- `editor`: کارشناس پنل با مجوزهای انتخابی.
- `viewer`: کاربر پنل با مجوز مشاهده؛ استفاده فقط در صورت اعطای صریح مجوز استفاده در سیاست بخش.

ادمین اصلی در «فعال و غیر فعال‌سازی امکانات» برای هر بخش، «مشاهده» و «استفاده و عملیات» را به نقش‌ها، نام‌های کاربری یا شناسه‌های پروژه اختصاص می‌دهد. مقادیر با ویرگول جدا می‌شوند. فهرست خالی یعنی ارث‌بری از مجوز فعلی؛ فهرست غیرخالی یک مخاطب محدود می‌سازد. تطابق هر یک از نقش، فرد یا پروژه کافی است، ولی شخص همچنان باید عضو پروژه باشد. اجازهٔ استفاده نیازمند اجازهٔ مشاهده نیز هست.

وضعیت «فقط ادمین اصلی» بر تمام مجوزهای فردی، نقشی و پروژه‌ای اولویت دارد. «غیرفعال» حتی ادمین اصلی را مسدود می‌کند. زیرصفحه‌های سئو و VM از محدودیت بخش والد نیز تبعیت می‌کنند. ادمین پروژه نمی‌تواند با فرم تنظیمات، محدودیت‌های نمایش ماژول‌ها را تغییر دهد.

تنظیمات مخاطبان در `panel/db/access_policy.json` هنگام ذخیره ساخته می‌شود؛ این فایل دادهٔ زمان اجراست و نباید با انتشار کد جایگزین شود. ذخیرهٔ سیاست فقط برای ادمین اصلی، با توکن CSRF ممکن است. فایل نامعتبر برای کاربران دیگر به معنای رد دسترسی است.

درخواست‌های مستقیم صفحه و POST، مجوزهای همان بخش را بررسی می‌کنند. عملیات شناخته‌شدهٔ مدیریت علاوه بر تب فعلی، مجوز بخش عملیات را بررسی می‌کنند. مدیر پروژه فقط اعضای پروژهٔ خودش را ویرایش می‌کند. مدیر دارای مجوز کاربران نمی‌تواند ادمین پروژه بسازد یا ویرایش کند یا مجوزی فراتر از مجوز خود بدهد.

اعتبار نشست از حسابی که واقعاً با رمز یا شمارهٔ تأییدشده وارد شده گرفته می‌شود؛ تشابه نام کاربری در دو پروژه به‌تنهایی عضویت مشترک ایجاد نمی‌کند. در ورود با رمز، فقط عضویت‌هایی که همان رمز ورودی را تأیید کنند وارد محدودهٔ نشست می‌شوند. حذف حساب، تغییر رمز یا لغو عضویت، دسترسی نشست قبلی را باطل می‌کند؛ تغییر نقش و مجوز از رکورد جاری دوباره خوانده می‌شود. نقش سراسریِ ذخیره‌شده در اعضای پروژه معتبر نیست. بعد از انتشار این نسخه، ورود مجدد به حساب برای نشست‌های قدیمی مدیران لازم است.

ترتیب منطقی تصمیم دسترسی: هویت معتبر ← پروژهٔ مجاز ← وضعیت جهانی و والد ماژول ← محدودیت همان پروژه ← مجوز مشاهده ← مجوز عملیات و CSRF ← محدودیت اختصاصی مسئول کار. «فقط ادمین اصلی» و محدودیت والد با انتخاب کاربر، نام قدیمی مجوز یا URL مستقیم دور زده نمی‌شوند. مجوز عملیات به‌تنهایی مجوز مشاهده ایجاد نمی‌کند. مجوزهای قدیمی مانند `size_chart`، `vm`، `seo`، `sale` و `prompt_hub` به کلید واحد همان بخش نگاشت می‌شوند؛ محدودیت قدیمیِ سخت‌گیرانه‌تر حفظ می‌شود.

فرم افزودن و ویرایش عضو از یک فهرست مجوز مشترک استفاده می‌کنند. مجوزهای قدیمی هنگام بازکردن فرم حذف نمی‌شوند؛ مدیر محدود فقط مجوزهایی را واگذار می‌کند که خودش اجازهٔ استفاده از آن‌ها را دارد. نام کاربری اعضای موجود توسط مدیر محدود تغییر نمی‌کند تا با حساب دیگری هم‌نام نشود. رمز یا هش ذخیره‌شدهٔ عضو در دادهٔ JavaScript ویرایشگر منتشر نمی‌شود.

پورتال نیز مشاهده و عملیات را جدا بررسی می‌کند: نمایش کتابخانه اجازهٔ ثبت رفرنس، رأی، تغییر اولویت یا تأیید تصویر نیست. مسئولان تأیید مرحله‌ای همچنان باید شرط اختصاصی مرحلهٔ پروژه را داشته باشند. ویرایش پروفایل و پشتیبانی حساب از عملیات محصولات جدا هستند. تقویم مجاز، کتابخانهٔ غیرمجاز را در JSON صفحه منتشر نمی‌کند؛ دادهٔ مرورگرِ تنظیمات فقط شامل گزینه‌های لازمِ نمایش تأییدهاست و رمز اتصال‌ها را ندارد.

VM و سئو پیش از بررسی مجوز، پروژهٔ واقعیِ فروشگاه یا کسب‌وکار را تعیین می‌کنند؛ تغییر `project_id`، `store_id`، `business`، slug یا مسیر زیبا، نقش پروژهٔ دیگری را به آن منبع منتقل نمی‌کند. عملیات تغییردهندهٔ API نیازمند POST و CSRF است. تنظیمات و کلید سراسری اتصال‌های سئو فقط در اختیار ادمین اصلی قرار دارند؛ انتخاب پارامتر نمایشی `role=admin` نقش واقعی کاربر را تغییر نمی‌دهد.

نام عملیات‌های AJAX و فرم‌ها در `AdminActionAccess` به بخش مربوط متصل است؛ فرستادن نام یک تب مجاز، مجوز عملیات بخش دیگری را ایجاد نمی‌کند. ارسال مستقیم عملیات به `admin.php` بدون پارامتر تب، بر اساس مجوز همان عملیات بررسی می‌شود. عملیات مشترک صف کار در استخراج و خروجی وب‌سایت، علاوه بر مجوز آن صفحه، بررسی اختصاصی محصول یا مسئول رفرنس را در هندلر حفظ می‌کنند.

بازیابی پشتیبان کامل پروژه، چون کاربران و تنظیمات دسترسی را نیز جایگزین می‌کند، فقط برای ادمین اصلی مجاز است. واردسازی محصول و موجودی از مسیر استخراج جدا باقی می‌ماند. افزودن عضو توسط مدیر پروژه یا مدیر دارای مجوز کاربران، عضویت هم‌نام آن فرد را در پروژه‌های دیگر تغییر نمی‌دهد.

API عمومی ردیابی و اتصال عامل‌ها همچنان قرارداد موجود خود را دارد، ولی محدودیت‌های بخش و سیاست مخاطبان بر آن اعمال می‌شود. عملیات API مرورگر نیازمند نشست ورود معتبر است.

آزمون سیاست‌ها: `php tests/access_control.php`

## مدیر کل بدون محدودیت و بازیابی تنظیمات

نقش `owner` مدیر کل بدون محدودیت است؛ حتی وضعیت غیرفعال و محدودیت ماژول پروژه را دور می‌زند. این نقش از فرم اعضای پروژه قابل تخصیص نیست. حساب‌های ادمین اصلی همیشه برای تعمیر تنظیمات دسترسی به صفحهٔ تنظیمات دارند؛ پس از ارتقای کد، یک‌بار از نشست قدیمی خارج و دوباره وارد شوید.

ادمین اصلی در تنظیمات پروژه، بخش «حساب مدیر کل سامانه»، می‌تواند حساب مدیر جدید را بسازد. حساب در `panel/db/system_admins.php` همان هاست، با هش رمز، ذخیره می‌شود. این فایل دادهٔ خصوصی زمان اجرا و خارج از Git است؛ در انتشار کد نباید حذف یا بازنویسی شود. درخواست مستقیم به فایل، محتویات آن را نمایش نمی‌دهد. ایجاد حساب نیازمند نشست ادمین اصلی و توکن CSRF است و حساب موجود را بازنویسی نمی‌کند.

روش CLI: `php tools/create-system-admin.php --username USERNAME --unrestricted`. رمز در ترمینال بدون نمایش خوانده می‌شود؛ آن را داخل آرگومان فرمان یا کد قرار ندهید. ساخت حساب در یک ماشین، آن حساب را روی ماشین/هاست دیگری ایجاد نمی‌کند.


درخواست‌های پشتیبانیِ بدون پروژه با هویت حساب تأییدشده ذخیره می‌شوند، نه فقط نام کاربری؛ دو حساب هم‌نام در پروژه‌های مختلف تاریخچهٔ خصوصی یکدیگر را نمی‌بینند. انتقال تاریخچهٔ قدیمی فقط وقتی خودکار است که همهٔ عضویت‌های هم‌نام با همان اعتبار ورود تأیید شده باشند؛ تاریخچهٔ مبهم برای ادمین اصلی باقی می‌ماند. پیشنهادهای تجاری نیز پیش از ویرایش/حذف از پروژهٔ مالک سند مجوز می‌گیرند؛ انتشار عمومی فقط مشاهده را باز می‌کند.

دادهٔ فرم اعضا و تنظیمات JavaScript با فهرست مجاز ساخته می‌شود؛ رمز اعضا و اطلاعات اتصال SQL/شبکه‌های اجتماعی به مرورگر فرستاده نمی‌شود. مسیرهای قدیمی چت و وظایف به همان کنترلرهای محافظت‌شدهٔ پنل متصل‌اند.
