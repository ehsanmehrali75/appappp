# بهبود سرعت و هم‌زمانی پنل — ۱۵ نوامبر ۲۰۲۶

مبنای شروع `6576e69` روی `main` و مخزن تمیز بود. این اصلاح برای کندشدن پنل هنگام فعالیت هم‌زمان پروژه‌ها، واردسازی، خروجی و آپلود انجام شد. تست‌ها روی داده و پایگاه موقت بودند؛ بار، PHP-FPM، دیسک، MySQL slow log و شبکهٔ هاست واقعی در این محیط قابل اندازه‌گیری نبودند.

## گلوگاه‌های تأییدشده و اصلاحات

1. **خواندن تمام کتابخانه‌ها در هر درخواست ادمین:** ابتدای `admin.php`، `getDB()` همهٔ پروژه‌ها را همراه محصولات، تقویم و لاگ‌ها بارگذاری می‌کرد؛ حتی هنگام آپلود یا نمایش یک پروژه. اکنون فهرست جدا و فقط‌خواندنیِ اطلاعات پروژه و اعضا استفاده می‌شود. تعداد کالا برای کارت مدیریت پروژه با `COUNT GROUP BY` خوانده می‌شود. صفحهٔ عمدیِ پایش فضای همهٔ پروژه‌ها و بعضی عملیات مدیریت اعضا هنوز دادهٔ کامل موردنیاز خود را می‌خوانند.
2. **خواندن تمام پروژه‌ها برای انتخابگر پورتال:** انتخابگر اکنون از فهرست فرادادهٔ پروژه‌های مجاز استفاده می‌کند. کتابخانهٔ پروژه‌های دیگر برای آن بارگذاری نمی‌شود. بررسی عضویت، انتخاب صریح پروژه و رد ثبت از تب قدیمی حفظ شده‌اند.
3. **تکرار DDL در هر اتصال:** راه‌اندازی قبلی، در هر درخواست چندین `ALTER TABLE ... MODIFY` و ده‌ها کنترل ستون را اجرا می‌کرد. در MySQL این کار می‌تواند پشت تراکنش نوشتن، منتظر metadata lock بماند و درخواست پروژهٔ دیگری را نیز معطل کند. اکنون نسخهٔ ساختار در جدول `maarksho_schema_versions` ثبت می‌شود؛ اتصال گرم فقط آن را می‌خواند و CREATE/ALTER انجام نمی‌دهد. مهاجرت اول با قفل بین فرایندها انجام می‌شود؛ فرایند منتظر، بعد از گرفتن قفل دوباره نسخه را بررسی می‌کند. نسخه فقط پس از اعتبارسنجی ستون‌های ضروری و ساخت ایندکس‌ها ثبت می‌شود؛ خطای مهاجرت موفق فرض نمی‌شود.
4. **نبود ایندکس‌های پروژه:** ایندکس بر `products(project_id)`، `schedules(project_id)`، `logs(project_id,at)` و `scraping_jobs(project_id,status)` اضافه شد. بررسی طرح اجرای SQL وجود ایندکس پروژه را تأیید کرد.
5. **محاسبهٔ فضای آپلود با جست‌وجوی تکراری:** مقایسهٔ هر فایل با آرایهٔ تمام مراجع محصول از جست‌وجوی خطی به lookup مجموعه تبدیل شد؛ این بخش از O(تعداد فایل‌ها × تعداد مراجع) به O(تعداد فایل‌ها + تعداد مراجع) می‌رسد. سهمیه و محاسبهٔ حجم با کش قدیمی جایگزین نشده‌اند.
6. **نگهداری بک‌آپ قبل از قفل worker:** در Cron ریشه، نگهداری بک‌آپ پیش از گرفتن lease سراسری اجرا می‌شد؛ چند درخواست رقیب می‌توانستند وارد آن شوند. اکنون بعد از گرفتن همان lease اجرا می‌شود. مسیر غیر-FPM که پاسخ `cron_required` می‌دهد، پردازش پنهانی بک‌آپ را شروع نمی‌کند.

هیچ کشی که مجوز، موجودی، تأیید تصویر یا اعتبار مالی را کهنه کند اضافه نشده است. مدل نقش‌ها و جداسازی پروژه تغییر نکرده است.

## نصب و کنترل روی هاست

- فایل‌های کد جدید نصب شوند؛ DB، uploads و تنظیمات واقعی حفظ شوند. پیش از تغییر ساختار، بک‌آپ کامل DB هاست موجود باشد.
- مهاجرت و ایندکس‌گذاری را ترجیحاً یک بار با PHP CLI هم‌نسخهٔ وب و از ریشهٔ پروژه، پیش از بازکردن ترافیک اجرا کنید:

```sh
php -r 'require "panel/inc/functions.php"; getConn(); echo "Schema ready\n";'
```

- ساخت ایندکس برای جدول بزرگ می‌تواند در اولین نصب زمان ببرد؛ timeout مهاجرت را با تکرار درخواست هم‌زمان دور نزنید. اجرای بعدی با نسخهٔ ثبت‌شده از DDL عبور می‌کند. هنگام افزودن مهاجرت جدید در آینده، `DatabaseSchema::VERSION` نیز باید تغییر کند.
- Cron واقعی هاست برای worker، یکپارچه‌سازی‌ها و نگهداری بک‌آپ حفظ شود. درخواست پس‌زمینهٔ مرورگر روی PHP-FPM همچنان یک worker PHP را تا پایان کار اشغال می‌کند؛ پاسخ سریع HTTP به معنی آزادشدن ظرفیت PHP-FPM نیست.
- پس از نصب، زمان پاسخ صفحات، صف PHP-FPM، `pm.max_children` و مصرف RAM هر پردازش، OPcache، slow query/metadata lock، I/O و فضای دیسک هنگام دو واردسازی/آپلود هم‌زمان اندازه‌گیری شوند. بدون این داده‌ها تعداد worker یا سقف RAM سرور تغییر داده نشده است.

## باقی‌مانده برای مرحلهٔ بعد

- کتابخانهٔ پروژهٔ انتخاب‌شده هنوز در بسیاری از صفحات کامل در حافظه و HTML قرار می‌گیرد. پروژهٔ بسیار بزرگ به صفحه‌بندی و فیلتر سمت سرور نیاز دارد؛ حذف بار پروژه‌های دیگر به معنی حل این بخش نیست.
- خروجی سنگین تصویر/ZIP و بعضی آپلودهای گروهی هنوز request-based هستند. قدم بعد صف پایدار با پیشرفت، لغو، ادامه و سقف هم‌زمانی هر پروژه است تا کار طولانی ظرفیت وب را مصرف نکند. وضعیت batch بعضی خروجی‌ها در session است؛ قفل session آن مسیر را بدون انتقال امن وضعیت به job store حذف نکرده‌ایم.
- محاسبهٔ فضا هنوز پوشهٔ مشترک آپلود را می‌بیند. برای تعداد فایل بسیار زیاد، فهرست فایل و رزرو حجم اتمی در SQL و تفکیک پوشهٔ پروژه‌ها مرحلهٔ بعد است.
- دفتر خصوصی حساب/اعتبار و تاریخچهٔ کارهای AI فایل مشترک دارند. انتقال تدریجی به دفتر SQL دارای ایندکس، تراکنش و آرشیو تاریخچه باید با حفظ رسید و جلوگیری از دوباره‌برداشت انجام شود؛ در این اصلاح دفتر مالی تغییر نکرد.
- برای سنجش ظرفیت واقعی، load test با دادهٔ مشابه مشتری و PHP-FPM/MySQL مشابه هاست لازم است؛ تست PHP تک‌پردازهٔ محلی معادل ظرفیت واقعی هم‌زمان نیست.

## اعتبارسنجی

- **۴۴۸ تست Python/HTTP موفق** در ۴۸۹٫۳۵۶ ثانیه، شامل سه رگرسیون جدید فهرست بدون محصولات، دوام نسخه و ایندکس، و خواندن HTTP زیر قفل نویسنده. زمان اجرای کل مجموعه معیار سرعت هاست نیست.
- بررسی نحو **۲۷۸ فایل PHP** و ۱۲ مجموعهٔ مستقل PHP موفق.
- هفت مجموعهٔ Chromium موفق: انتخاب میزکار/دو تب، ساخت کاربر، نمای کلی پروژه، گالری پورتال، استودیو سایز، واردسازی و بازگردانی ۱۰۰۰ ردیف، و وردپرس. خطای JavaScript گزارش نشد.
- چهار رگرسیون MariaDB واقعی موفق: تست جدید هم‌زمانی و صفر بودن DDL اتصال گرم، عضویت/rollback، پشتیبانی با مهاجرت charset/engine، و snapshot بزرگ ERP با سقف packet برابر ۴ MiB. پایگاه‌ها و کانتینر موقت پس از اجرا حذف شدند.
- YAML گردش CI و سازگاری ۱۶ فایل ZIP اپ تیام با منبع تأیید شدند. تست تازهٔ MySQL به CI اضافه شده است؛ اجرای آن در GitHub پس از انتشار با اجرای محلی یکی فرض نشده است.

رگرسیون اختصاصی SQLite و HTTP:

```sh
PHP_BINARY=php python -m unittest discover -s tests -p 'test_panel_performance.py'
```

رگرسیون MariaDB/MySQL روی سرور آزمایشی با مجوز ساخت و حذف دیتابیس، هرگز حساب دیتابیس تولید:

```sh
PERFORMANCE_TEST_MYSQL_PORT=33306 PERFORMANCE_TEST_MYSQL_PASSWORD=fixture-password php tests/performance_mysql.php
```

آزمون MariaDB به CI اضافه شده است. خروجی این تست فقط زمان، شمار DDL و وضعیت تأیید را گزارش می‌کند؛ کلید یا اطلاعات مشتری وارد گزارش نمی‌شود.
